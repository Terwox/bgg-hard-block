# Audit recommendations — bgg-hard-block

Scoped 2026-08-15 against version 0.3.15 (main). Each row is a self-contained audit task for the bgg-hard-block Chrome extension, sized for the suggested ChatGPT 5.6 model and reasoning effort. Axes: security, human readability, speed.

| recommendation | model suggested to use | model effort to use |
| --- | --- | --- |
| Adversarially audit `src/page-bridge.js` for any code path where the captured `GeekAuth` authorization header (`authHeader`) can reach `publish()`, the Document Object Model (DOM), `localStorage`, `chrome.storage`, an error message, or any network destination other than `https://api.geekdo.com` — including through error objects thrown by `fetchApi` and the `status: "error"` payload published by `syncBlockList`. This is the repo's own stated top audit question (SECURITY.md "In scope"). | gpt-5.6-codex | xhigh |
| Threat-model the `<meta>` element bridge (`bgg-hard-blocker-data`, `bgg-hard-blocker-settings`): both elements and their CustomEvents are writable/dispatchable by BoardGameGeek (BGG) page scripts. Determine the worst case if a hostile page forges the data payload — e.g. `src/content.js` adopting an attacker-chosen block list (censoring arbitrary users, persisted via `writeStatus` into `chrome.storage.local`) or `src/settings-bridge.js` `storeSubscriptionState()` writing forged counters — and whether any forged payload can trigger network writes (`PUT .../blocks`). | gpt-5.6-codex | xhigh |
| Verify the consent gate end to end: no BGG data is read, no interceptor installed, and no request made before a current consent record exists. Check all six copies of the `DISCLOSURE_VERSION` ladder (`src/background.js`, `src/content.js`, `src/settings-bridge.js`, `src/popup.js`, `src/options.js`, `src/onboarding.js`) agree for every version pattern, and that consent withdrawal in `acceptSettingsPayload` (`src/page-bridge.js`) fully disarms already-installed fetch/XMLHttpRequest wrappers. | gpt-5.6-codex | high |
| Audit the subscription-block write path (`addSubscriptionBlock` / `reconcileSubscriptionBlocks` / `queueSubscriptionSync` in `src/page-bridge.js`): confirm the additions-only invariant (no code path can remove a block), that the user identifiers being `PUT` can only originate from BGG's own `/api/userblock` response, and that `normalizeApiLink` origin pinning cannot be bypassed via redirects, protocol-relative links, or unicode host tricks. | gpt-5.6-codex | high |
| Test the blocked-content matchers for bypasses: `normalizeUsername`, `usernameFromProfileHref`, `quoteUsername`, and the `BBCODE_QUOTE_TOKEN` regex in `src/content-core.js`. Look for crafted usernames or BBCode (nesting, unbalanced tags, encoding, homoglyphs, locale casing) that let a blocked user's content evade `filterDom` or `sanitizeBlockedQuotes`, and for regular-expression denial-of-service (ReDoS) risk on attacker-sized inputs. | gpt-5.6-codex | high |
| Sweep all files in `src/` for injection sinks: `innerHTML`, `insertAdjacentHTML`, `document.write`, `eval`, `Function`, attribute-based script vectors. Confirm popup/options/onboarding render BGG-derived strings only via `textContent`, as `src/popup.js` claims. | gpt-5.6-codex-mini | low |
| Check manifest and permission minimality: `manifest.json` requests only `scripting` + `storage` and one host permission — verify each is exercised, that the three URL-pattern lists (`manifest.json` `content_scripts[].matches`, `DISCUSSION_TAB_PATTERNS`, and `DISCUSSION_PATH_PATTERNS` in `src/background.js`) are exactly equivalent, and that `isDiscussionUrl` rejects lookalike hosts, other schemes, and subdomains. | gpt-5.6-codex-mini | medium |
| Review supply-chain posture: pin GitHub Actions in `.github/workflows/ci.yml` to commit SHAs (currently `@v4`/`@v5` tags), audit `scripts/package.sh` + `scripts/make_zip.py` for anything that could break the byte-for-byte reproducibility guarantee in BUILD.md, and decide whether committed `artifacts/*.zip` files belong in the repo. | gpt-5.6-codex-mini | medium |
| Cross-check PRIVACY.md and SECURITY.md claims against the code: enumerate every `chrome.storage.local` key and `localStorage` key actually written (`bggHardBlockerConsent`, `bggHardBlockerOptions`, `bggHardBlockerState`, `bggHardBlockerSubscriptionState`, `bgg-hard-blocker-profile-cache-v1`) and confirm the disclosure lists all of them, nothing more, and that reply-draft text is provably never persisted. | gpt-5.6-codex | medium |
| Audit the Python helper scripts (`scripts/live_smoke.py` ~457 lines, `browser_test.py`, `capture_page.py`, `spa_route_smoke.py`) for security hygiene: how live-session credentials or cookies are supplied and cleaned up, subprocess argument handling, and whether any script could leak an authenticated session into logs or fixtures. | gpt-5.6-codex-mini | medium |
| Readability review of `src/content.js` (589 lines, one async IIFE with ~15 module-level mutable flags governing reveal/quarantine/cache races): assess whether the reveal state machine (`allowReveal`, `cacheSettled`, `domReady`, `hasBlockList`, `source`) can be expressed more legibly, and propose behavior-preserving decomposition compatible with the no-build-step constraint. | gpt-5.6 | medium |
| Evaluate duplication for consolidation: the `DISCLOSURE_VERSION` ladder is pasted verbatim into six files, and `collectElements`/`canonicalPost`/JSON-payload readers are each implemented twice-plus across `src/content-core.js`, `src/content.js`, `src/page-bridge.js`, `src/settings-bridge.js`. Recommend whether a shared module is worth it given the project's explicit no-bundler, diffable-source policy, or whether a lint/test that asserts the copies match is the better trade. | gpt-5.6 | medium |
| Comment-accuracy pass: the codebase is unusually heavily narrated (auditing notes, invariants, "load-bearing" phrasing). Verify each substantive comment still matches the code it describes at v0.3.15, flagging stale or overclaiming comments — in a security-audit-oriented codebase a wrong comment is a vulnerability multiplier. | gpt-5.6 | medium |
| Docs-drift check across README.md, BUILD.md, STORE_LISTING.md, and the onboarding/options page copy: confirm feature lists, install steps, the "five questions" audit table, and store screenshots still match 0.3.15 behavior (e.g. profile-name redaction and thumbs-popover handling are newer features). | gpt-5.6 | low |
| Profile the MutationObserver pipeline in `src/content.js` on long threads: observer covers `documentElement` with `subtree`, `characterData`, and a six-attribute filter; every burst also schedules a 75 ms debounced full-document `filter(document)` sweep. Measure callback cost and full-sweep frequency on a 500+ post thread and recommend whether the whole-document backstop can be narrowed or made incremental. | gpt-5.6-codex | high |
| Review per-call overhead in `src/content-core.js`: `filterDom` rebuilds the normalized blocked-username Set (`makeBlockedSet`) on every invocation — including every mutation burst — and `collectPosts`/`collectElements` run overlapping `querySelectorAll` scans. Quantify the cost with a realistic block-list size and propose caching the normalized set keyed on list identity. | gpt-5.6-codex | medium |
| Measure real first-paint latency introduced by the reveal hold: `POST_LOAD_MAX_HOLD_MS` (500 ms) in `src/content.js` plus the 2-second Cascading Style Sheets (CSS) failsafe in `src/content.css`. Determine typical time-to-reveal on warm-cache, cold-cache, and signed-out visits, and whether the cached-list path can safely release earlier. | gpt-5.6-codex | medium |
| Review `resolveBlockedProfiles` in `src/page-bridge.js`: on a cold profile cache it fires one API request per blocked user in an unbounded `Promise.all`. Assess rate-limit and latency impact for large block lists (50+ users) and recommend a concurrency cap or batched endpoint if BGG offers one. | gpt-5.6-codex-mini | medium |
